버프창이 밀려서 안 보이는 버프를, 지속시간을 감안해 따로 표시하는 오버레이.

## ⚠️ 전제조건

**게임을 '테두리 없는 창 모드'로 실행해야 합니다.**
전체화면 모드에서는 외부 오버레이가 표시되지 않습니다.

## 실측값

버프바는 **하단 중앙, HP 바 바로 위**에 있다.

**중요: 같은 1920x1080이라도 UI 배율에 따라 아이콘 크기가 다르다.**

| | 배율 A | 배율 B |
|---|---|---|
| 아이콘 | 21 x 21 px | 26 x 26 px |
| 피치 | 23.33 px | 29.0 px |
| 간격 | ≈2.33 | 3.0 |
| 한 줄 최대 | ? | **16칸** |

값을 하드코딩할 수 없으므로 `grid_detect.py`가 자동 검출한다.

```bash
python capture.py --auto                          # 캡처하며 자동 검출
python capture.py --annotate <파일> --auto        # 기존 파일에서 검출
```

두 실측 케이스 모두에서 셀/피치를 정확히 복원하는 것을 확인했다.

### 레이아웃 (배율 B 기준)

```
y 900~913   스택 표시    "X 4"  (아이콘 위, 청록색)
y 914~939   아이콘 행     26px
y 940~959   지속시간      "7초" "53분"  (아이콘 아래)
y 962~      HP 바
```

### 지속시간 표시

아이콘 **아래**에 텍스트로 붙는다. 글자 높이는 약 8px.

- 단위가 함께 표시된다: `7초`, `53분`, `13분`
- 1초 미만에서는 소수점 한 자리: `0.3초`
- **분 단위는 추적하지 않는다.** 대상 버프가 모두 초 단위이고,
  `분`과 `초`는 둘 다 8px 폭에 획이 끊기는 한글이라 서로 오인되기 쉽다.
  `53분`을 `53초`로 잘못 읽으면 3180초 버프가 53초로 표시되어
  오히려 방해가 되므로 아예 후보에서 뺐다 (`--minutes`로 활성화 가능).
- **모든 버프에 표시되지는 않는다.** 배율 A 케이스에서는 4개 중 1개뿐이었다.
  → `Observation.remaining=None` 폴백 경로가 실제로 필요하다
- 텍스트 폭이 아이콘보다 넓어 옆 칸을 침범한다 (`53분` = 30px > 26px)
  → 셀 단위로 자르면 안 되고, 텍스트 덩어리의 중심 x로 아이콘에 배정해야 한다

### 색상 구분

텍스트와 테두리 색이 대응한다. HSV 실측:

| 색 | H (OpenCV 원시값) | 실제 각도 | 예시 |
|---|---|---|---|
| 녹색 | ≈49 | **≈98도** | 7초, 19초, 53분 |
| 주황 | ≈25 | **≈50도** | 2초, 4초, 22초 |

> OpenCV의 H는 0~179 범위라 실제 각도의 절반이다. 코드에서 각도로
> 비교할 때는 2를 곱해야 한다. `text_color_mask`가 쓰는 값이 실제
> 각도 기준(100도/50도)인 이유다.

의미는 미확정. 남은 시간이 짧을 때 주황으로 바뀌는 것으로 보이나
(2초/4초가 주황) 22초도 주황이라 단순 임계값은 아니다.
버프/디버프 구분일 가능성도 있다.

### 스택 표시

아이콘 **위쪽**에 `X 4` 형태로 붙는다. 현재 `BuffTracker`는 스택을
지원하지 않는다. 필요하면 `BuffState`에 스택 수를 추가해야 한다.

### 맨 앞 녹색 `+` 칸은 오버플로 표시다

버프 표기 한도를 넘으면 맨 앞에 `+` 칸이 생기고, **아래 숫자는 초과한
버프 수**다(사용자 확인).

> 이 문서는 원래 이 칸을 "회복 물약 퀵슬롯"이라고 적어 두었으나
> 사실이 아니다. 그 설명을 믿고 `--ignore`로 등록하면 초과 버프 수를
> 통째로 버리게 된다. 실제로 그렇게 등록했다가 되돌린 적이 있다.

`overflow_counter`로 등록해두면 버프가 아니라 카운트로 해석된다.
실측 대조: 등록본과 해밍 5 / Hue차 0.2로 일치했고, 아래 숫자도
`1`(초과 1개)로 읽혔다.

정체를 모르는 칸은 `--ignore`로 등록하지 말 것. 무시로 등록하면 그 칸이
결과에서 통째로 빠져, 실제로 의미가 있었을 때 조용히 놓친다.
등록하지 않고 두면 미인식으로 남아 나중에 알아차릴 수 있다.

### 미확정

- **정렬 방향.** 두 스크린샷의 UI 배율이 달라 좌표를 직접 비교할 수
  없다. 같은 배율에서 버프 개수가 다른 두 프레임이 필요하다.
- 16칸을 넘으면 어떻게 되는지 (줄바꿈 / 밀림 / 잘림)
- 색상 구분의 의미

## 텍스트 파싱

`text_parse.py`가 담당한다. 범용 OCR(Tesseract 등)을 쓰지 않는 이유는
8px 높이 글자에서 정확도가 낮고, 10Hz로 16개 영역을 돌리기엔 느리기
때문이다. 폰트가 고정이므로 글자 단위 템플릿 매칭이 낫다.
필요한 템플릿은 11개뿐이다: `0`~`9`, `.`, `초`.
(`분`은 제외 — 위 "지속시간 표시" 참고)

### 분할 파이프라인

```
텍스트 행 크롭
  → 마스크 만들기 (색 / top-hat / 밝기 — 아래 "배경 밝기 대응")
  → 연결 성분
  → 세로 병합    ('초'/'분'은 획이 끊겨 여러 성분이 된다)
  → 수직 투영 분할 ('7초'처럼 1px로 닿아 붙은 글자를 나눈다)
  → 노이즈 조각 제거 (글자 높이에 못 미치는 것. 소수점은 예외)
  → 그룹화       (x가 가까운 글자 = 버프 하나의 표기)
  → 중심 x로 아이콘에 배정
  → 템플릿 매칭  (마스크별 후보 중 먼저 읽히는 것 채택)
```

세로 병합과 수직 분할이 둘 다 필요한 이유가 상반돼 보이지만, 판단
기준이 다르다. 병합은 x가 **크게 겹치는** 조각(한글 획), 분할은 x가
**이어지되 골짜기가 깊은** 지점(다른 글자)을 본다.

### 소수점 처리

소수점은 높이가 1~2px다. `min_h`를 4 이상으로 두면 `0.3초`가
`03초`로 읽히므로 2로 낮췄다. 대신 들어오는 노이즈는 템플릿 매칭
점수(`min_score`)에서 걸러진다.

### 배경 밝기 대응

밝기 하나로 자르면 배경이 밝은 장면(수련장 금색 바닥, 폭발 이펙트)에서
무너진다. 그래서 **한 칸마다 여러 방식으로 후보를 만들고, 먼저 읽히는
것을 쓴다** (`Recognizer.cell_glyph_candidates`).

| 방식 | 근거 | 강한 상황 |
|---|---|---|
| `text_color_mask` | 글자 색이 녹색/주황으로 고정 | 대부분. 가장 정확 |
| `text_tophat_mask` | 획은 '바로 옆'보다 밝다 | 배경이 밝아 색이 겹칠 때 |
| `adaptive_binarize` (행 전체) | 밝기 | 배경이 고를 때 |
| `adaptive_binarize` (칸별) | 밝기 | 화면 일부만 밝을 때 |

실측 정확도 (초 단위 표기 기준):

    전투 (어두움):   13/13,  오독 0
    수련장 (밝음):    7/11,  오독 0

> 주의: 색 임계값은 실제 각도 기준이다. OpenCV의 H는 0~179라 실제
> 각도의 절반이므로, 다른 문서에서 본 `H≈49`는 실제로는 98도다.
> 이 값을 그대로 쓰면 녹색 글자를 통째로 놓친다.

못 읽는 경우의 방어는 그대로다. **잘못 읽느니 못 읽는 편이 낫다.**

- `segment_glyphs`의 `max_fill`: 켜진 비율이 45%를 넘으면 배경을
  글자로 오인한 상황이므로 빈 목록 반환 (색 마스크가 배경색과
  겹쳐 가득 찼을 때 여기서 걸린다)
- `read_group`의 `min_score`: 한 글자라도 확신이 없으면 그룹 전체 실패
- `to_seconds`의 `MAX_SECONDS`(300초): 초 단위 버프에 나올 수 없는
  크기면 숫자를 잘못 읽은 것으로 보고 버린다
- 실패한 셀은 `remaining=None`이 되고, 고정 duration이 없으므로
  그 버프는 아예 추적하지 않는다

```bash
python glyph_tool.py preview captures/frame.png --y 941 957
```

## 파이프라인

`pipeline.py`의 `Recognizer`가 프레임 한 장을 `Observation` 목록으로 바꾼다.

```
프레임
  ├─ 아이콘 행 → 그리드 → dHash+Hue → buff_id
  └─ 텍스트 행 → 이진화 → 글자 분할 → 템플릿 → 남은 시간
                              ↓
                      중심 x로 셀에 배정
                              ↓
                  Observation(buff_id, remaining)
                              ↓
                      BuffTracker.update()
                              ↓
                        오버레이 렌더
```

### 그리드는 캐시된다

UI 배율은 세션 중에 바뀌지 않으므로 한 번 검출하면 재사용한다.
이건 성능 문제가 아니라 **정확성 문제**다. 버프가 1개만 남으면
피치를 추정할 수 없으므로, 캐시가 없으면 그 순간 인식이 끊긴다.
인식이 30프레임 연속 비면 배율이 바뀐 것으로 보고 다시 잡는다.

### 오버플로 카운터

버프 표기 한도를 넘으면 맨 앞에 카운터 칸이 생기고, 아래 숫자로
몇 개가 밀렸는지 표시된다. `OVERFLOW_ID`로 등록해두면 버프가 아니라
카운트로 해석된다.

이건 **검증용**이지 필수가 아니다. 밀림 대응은 상태 머신이 이미
해결했다. 카운터의 가치는 일관성 검사에 있다:

    추적 12 = 화면 9 + 오버플로 3   ✓
    추적 10 ≠ 화면 9 + 오버플로 3   → 인식을 놓쳤다
    추적 15 ≠ 화면 9 + 오버플로 3   → 타이머가 실제보다 오래 살아 있다

`consistency_gap()`이 이 차이를 반환한다. `--debug`로 확인할 수 있다.

> 카운터 숫자는 **초과분**이다(사용자 확인). 총합이 아니다.
> `consistency_gap()`이 그 전제로 계산한다.

## 아이콘 인식

`icon_match.py`가 담당한다. **dHash(모양) + 평균 Hue(색상)** 를 함께 쓴다.

### 왜 dHash만으로는 부족한가

서폿 버프 4종은 실루엣과 이펙트 배치가 사실상 동일하고 색만 다르다.
dHash는 흑백 기반이라 이런 조합에서 마진이 좁다. 실측 해밍 거리:

| | red | gold | blue | purple |
|---|---|---|---|---|
| red | 0 | 12 | 14 | **8** |
| gold | 12 | 0 | 12 | 12 |
| blue | 14 | 12 | 0 | 12 |

반면 평균 Hue는 최소 46도 떨어져 있어 아주 잘 갈린다.

    red 9도  /  gold 55도  /  blue 205도  /  purple 295도

### 1px 시프트가 가장 큰 위험

dHash 강건성 실측 (같은 아이콘의 자기 해시와의 거리):

| 변형 | 거리 |
|---|---|
| 밝기 ±30% | 0~5 |
| JPEG 재압축 (q40~60) | 0~3 |
| 반투명 이펙트 | 0~1 |
| **크롭 1px 어긋남** | **11~15** |

배경 변화나 압축에는 매우 강한데, **정렬이 1px만 어긋나면 서로 다른
아이콘 간 거리보다 멀어진다.** 그래서 매칭 시 ±1px 시프트를 모두
시도해 최소 거리를 쓴다 (거리 15 → 8로 감소 확인). 비용은 XOR 9번이라
무시할 수준이다.

### 임계값 근거

같은 프레임의 16칸 전체로 검증했다.

    정탐 (1px 시프트 포함):  해밍 0~8,  Hue 0~2도
    오탐 (가장 가까운 남):    해밍 13,   Hue 35도

→ `MAX_HAM=10`, `MAX_HUE_DEG=20`. 처음 잡았던 14/40은 전혀 다른
아이콘(금색 폭발 이펙트)을 sup_red로 오인했다.


배경이 다른 장면에서 같은 버프를 2~3장씩 등록하면 더 안정적이다.
`--inset 2`로 테두리를 잘라내는데, 테두리 색은 버프 종류가 아니라
상태(버프/디버프)에 따라 바뀌므로 특징에서 빼는 편이 낫다.

## 게임 접속하면 할 일

1. `roi_picker.py --name buffbar` 로 버프바 영역을 잡는다.
   돋보기가 뜨니 픽셀 단위로 경계를 맞출 수 있다.
2. `capture.py --frames 30 --interval 1` 로 버프가 쌓였다 사라지는
   과정을 담는다.
3. `capture.py --annotate <파일> --grid 21x2.33` 로 격자를 덧그려
   셀 경계가 아이콘과 맞는 값을 찾는다. 숫자를 바꿔가며 반복.
4. 캡처를 보고 세 가지를 확인한다.
   - 아이콘 한 변 크기와 간격
   - 남은 시간 표현: 숫자 / 부채꼴 게이지 / 표시 없음
   - 신규 버프가 앞에 들어오는지 뒤에 붙는지

3번이 중요하다. 셀 경계가 어긋나면 각 셀의 해시가 전부 흔들려
dHash 매칭이 아예 동작하지 않는다.

## 설계 원칙

### 1. 인식(observation)과 상태(state)의 분리

이 프로젝트의 핵심입니다. 버프바에서 안 보인다고 버프가 끝난 게 아닙니다.
밀려서 ROI 밖으로 나갔을 뿐일 수 있습니다.

**버프 제거 조건은 오직 `now >= expire_at` 하나입니다.**
미관측은 절대 소멸 근거가 아닙니다. 한 번 인식한 버프는 버프칸에서
밀려나 보이지 않아도, 인식 시점의 시간에서 계속 흘러갑니다.

`test_many_empty_frames_do_not_expire`가 이걸 지킵니다. 리팩터링 중
"안 보이면 지운다" 로직이 들어가면 여기서 잡힙니다.

### 2. 갱신은 재관측으로 자연 처리

로아는 버프 갱신 시 아이콘이 앞으로 당겨집니다. 따라서 갱신되면
자동으로 관측 범위에 들어오고, `expire_at`이 실측값으로 덮어써집니다.
별도의 키 훅이나 갱신 감지 로직이 필요 없습니다.

### 3. 신뢰도 구분

- `observed` — 지금 보이는 중. 실측 기반. 실선 테두리
- `predicted` — 밀려서 안 보임. 추정. 점선 테두리 + 반투명

추정 타이머가 어긋났을 때 유저가 그걸 딜사이클에 쓰면
툴이 없느니만 못하므로, 시각적으로 반드시 구분합니다.

### 4. UI 경계는 직렬화 가능한 dict

`tracker.event(now)`가 그대로 WebSocket에 실을 수 있는 형태입니다.
나중에 Tauri로 UI를 옮길 때 인식 파이프라인 쪽을 건드리지 않기 위함입니다.

```json
{"type": "buff_update", "t": 12.4, "buffs": [
  {"id": "emperor", "name": "황제", "remaining": 8.4,
   "total": 12.0, "progress": 0.7, "confidence": "observed",
   "priority": 0, "color": "#ffb300"}
]}
```

## 알려진 한계

**스택형 버프는 미지원입니다.** 실측에서 `X 4` 표기를 확인했습니다.
필요해지면 `BuffState`에 스택 수를 추가하면 됩니다.

**사망 시 처리는 미확인입니다.** 사망으로 버프가 사라지는지 확인되면
`tracker.flush()`를 호출할 트리거만 붙이면 됩니다.

> 강제 해제(해제기 등)로 인한 조기 종료는 **없는 것으로 확인**됐습니다.
> 따라서 타이머 기반 만료가 실제와 어긋날 경우가 사실상 없습니다.

## buffs.json 채우기

`python buff_editor.py`로 아이콘을 보면서 이름을 붙이는 것을 권합니다.
ID를 바꾸면 `icons.json`과 `icon_images/`까지 함께 옮겨 줍니다.

**고정 `duration`은 쓰지 않습니다.** 같은 버프라도 어떤 스킬로
걸었느냐에 따라 지속시간이 달라져, 고정값을 넣으면 틀린 타이머를
보여주게 됩니다. 남은 시간은 **화면의 지속시간 표기를 읽어서만**
채웁니다. 읽지 못한 버프는 아예 추적하지 않습니다 —
"잘못 읽느니 못 읽는 게 낫다"는 원칙의 연장입니다.

`type`이 `instant`인 버프(즉발형)는 타이머 대상에서 제외됩니다.
지속시간이 없는 것까지 바에 남기면 화면이 다시 지저분해져
원래 고치려던 문제로 돌아갑니다.
